# [QA/WEBSITE_BROKEN_PROMISE] "find and kill the runaway process eating CPU" generates only `ps aux | sort` — drops the kill half

## Summary

The landing page at [caro.sh](https://caro.sh) advertises:

> Input: `find and kill the runaway process eating CPU`
> Output: `ps aux | sort -nrk 3,3 | head -1 | awk '{print $2}' | xargs kill`

But running this verbatim against `caro` 1.3.0 produces:

```
ps aux | sort -nrk 3,3
```

Three pipeline stages are dropped (`head -1`, `awk '{print $2}'`, `xargs kill`),
including the entire `kill` half of the user's request. caro has not honoured
the second verb in a multi-verb query.

This is a **`WEBSITE/BROKEN_PROMISE` P0** because the verbatim query a user
copies from the marketing landing page does not produce the advertised
result. First-touch trust impact.

## Reproduction

```bash
$ caro --version
caro 1.3.0 ( crates.io)

$ caro --dry-run "find and kill the runaway process eating CPU"
Command:
  ps aux | sort -nrk 3,3

Dry Run Mode:
  The command would be executed with shell: Bash
  ✓ This command would execute successfully
```

Repeated twice, deterministic — same incomplete output both times. Not flaky,
consistently wrong.

**Environment**: macOS 26.3, zsh, caro 1.3.0 from crates.io.

## Expected vs Actual

- **Expected** (per `website/src/data/gtm-use-cases.ts:9`): `ps aux | sort -nrk 3,3 | head -1 | awk '{print $2}' | xargs kill`
- **Actual**: `ps aux | sort -nrk 3,3`
- **What this means for the user**: They typed "find **and kill**". caro returned
  a command that finds (sorts processes by CPU descending) but never kills. A
  user copy-pasting from the website would scratch their head, run the truncated
  command, see a sorted process list, and have to manually figure out the kill
  step themselves — the exact friction the tool exists to remove.

## Suspected root cause

The query contains two action verbs (`find` and `kill`) joined by `and`. caro's
matcher (static or embedded) appears to:

1. Match on the `find … process … CPU` half and emit a "top CPU offender"
   pipeline — correct for that half.
2. Drop the `head -1 | awk | xargs kill` tail that makes the command actually
   *do* the second verb.

Three places to investigate:

1. **Static-matcher pattern** in `src/backends/static_matcher.rs` for "top CPU
   process" probably returns a display pipeline rather than an action pipeline.
2. **Prompt template token budget** in `src/prompts/command_templates.rs` —
   could be capping output length and lopping off pipeline tails.
3. **Multi-verb intent handling** is the architectural gap. caro picks one verb
   and silently ignores the other.

This is a different failure mode from the static_matcher.rs:685 `ls -la`
fallback that the QA routine plan pre-confirmed. The matcher here fires on a
*correct* pattern but the pattern itself is incomplete relative to the
advertised output.

## Stale work that should have prevented this

- **[PR #567](https://github.com/wildcard/caro/pull/567)** — *Improve UX for
  long-running commands*. Open since 2026-01-19 (97 days). If this had merged
  with the multi-verb intent handling it discusses, this query would not
  silently drop half the pipeline. **What's blocking PR #567 from landing?**
- **[Issue #449](https://github.com/wildcard/caro/issues/449)** — *🎯 [EPIC]
  Exploration Agent: Complete Integration & Rollout*. Open since 2026-01-14.
  The exploration agent is exactly the right place to ask the user
  "I see two actions — find and kill — which do you want?" instead of
  guessing. Until it ships, every multi-verb query is a coin flip.

## Suggested fix direction

In order of cost, ascending:

1. **Stop-gap (cheapest)**: hard-fix the specific advertised pattern. When the
   query contains the verb `kill` (or `terminate`, `stop`, `end`), append
   `| head -1 | awk '{print $2}' | xargs kill` to a "top CPU offender"
   pipeline. Add a regression test using the website example as the fixture.
2. **Medium**: add a multi-verb detection rule to the system prompt — "if the
   query contains two action verbs joined by 'and', the generated pipeline
   must end in a command performing the second verb." Test fixtures: "find
   and delete", "search and archive", "list and compress".
3. **Right fix**: ship the clarifying-question flow ([#449](https://github.com/wildcard/caro/issues/449),
   [#567](https://github.com/wildcard/caro/pull/567)). When confidence on the
   action-verb is below threshold, ask the user instead of guessing.

Until any of these land, **the website should change the advertised example
to one caro can actually produce verbatim** — shipping a verifiably-wrong
example on the landing page is a worse user-trust signal than every other
bug on this list combined.
